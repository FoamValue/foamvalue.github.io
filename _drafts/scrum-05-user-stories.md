## 什么是用户故事

用户故事（User Story）是 Scrum 里描述需求的标准格式。它不是需求文档，而是一张"便签"——足够简单，但信息完整。

**标准格式：**

> 作为一个 **<角色>**，我想要 **<功能>**，以便 **<价值>**。

**例子：**
> 作为一个**网购用户**，我想要**在订单页面查看物流信息**，以便**知道包裹到哪了**。

## 好故事的 INVEST 原则

| 原则 | 含义 | 反面例子 |
|------|------|---------|
| **I**ndependent | 独立，不依赖其他故事 | "先做完登录才能做支付" |
| **N**egotiable | 可协商，细节可以讨论 | "需求写死了，不能改" |
| **V**aluable | 有用户价值 | "重构数据库"（用户看不到价值） |
| **E**stimable | 可估算，团队知道大概工作量 | "做一个智能推荐系统"（太大） |
| **S**mall | 够小，一个 Sprint 能做完 | "做一个电商平台" |
| **T**estable | 可测试，有明确的验收标准 | "让体验更好"（怎么算好？） |

## 故事点估算

故事点（Story Points）是团队估算工作量的单位，不是时间。

**为什么不用「人天」？**
- 每个人效率不同，同样的功能 A 要 1 天，B 要 3 天
- 估算时间容易变成"承诺"
- 故事点注重的是**相对大小**，不是绝对时间

**Fibonacci 数列估算：** 1, 2, 3, 5, 8, 13, 21

团队先找一个"基准故事"作为 3 点，然后其他故事对比它来估算。

## Planning Poker（计划扑克）

团队一起估算的工具：

1. PO 讲一个故事
2. 每个人用自己的牌私下出点数
3. 同时亮牌
4. 点数差异大的（比如有人出 3，有人出 13），分别解释理由
5. 讨论后再出一轮，直到意见趋同

**这个过程的价值不在于估算结果，而在于讨论过程**——大家会暴露对需求的不同理解，提前发现坑。

## 存量与速率

- **Velocity（速率）**：团队一个 Sprint 能完成的故事点总数
- 连续 3-4 个 Sprint 后，Velocity 趋于稳定
- PO 用 Velocity 预测未来：还剩 100 点，速率 20 点/Sprint，大约 5 个 Sprint 做完

## 一句话总结

用户故事把需求变成了"谁要什么、为什么"，故事点把工作量变成了"相对大小"。**好的故事 + 靠谱的估算 = 可预测的交付。**
