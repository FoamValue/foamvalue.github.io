AI 工具已经渗透进日常开发的方方面面——写代码、改 Bug、生成测试用例、甚至做架构评审。但很多开发者的使用方式还停留在"遇到问题问一句"的阶段，AI 的输出零散且不可控，反而增加了筛选和纠错的成本。

真正高效的用法，是把 AI 嵌入到开发流程的每个环节，形成一套**可复用的工作流**。

这篇文章梳理一条完整的链路：**需求分析 → 架构设计 → 代码实现 → 测试用例 → 自动化验证**，逐一讲清每个环节里 AI 和人的分工边界。

![AI 辅助开发工作流流程图](/assets/images/ai-dev-workflow.svg)

## 需求与拆分需求

### 模糊需求是常态

项目启动时的需求往往是模糊的："做一个博客系统"、"优化一下页面加载速度"、"加个支付功能"。人能凭经验脑补上下文，但 AI 需要更结构化的输入才能给出有价值的输出。

### 用 AI 拆解需求

把模糊需求直接发给 AI，让它帮你拆解成可执行的子任务：

> **你：** "我想做一个博客系统，帮我拆解一下需求"
>
> **AI：** 可以从三个维度拆分：
> 1. **功能需求**：文章管理（CRUD）、用户系统（登录注册）、评论互动
> 2. **数据需求**：MySQL 表结构设计、Redis 缓存策略
> 3. **非功能需求**：首屏加载 < 1s、安全性（防 XSS/SQL 注入）

![需求拆分过程](/assets/images/req-breakdown.svg)

AI 的拆解速度很快，而且通常能覆盖你遗漏的维度——比如你可能只想到功能需求，忘了考虑安全和性能。

### 人的工作：筛选与决策

AI 的拆分是"广度优先"的——它会列出所有可能性，但不会替你判断优先级。你需要做的是：

- **删减**：砍掉当前阶段不需要的部分，MVP 不等于全功能
- **排序**：确定哪些先做、哪些后做，哪些可以并行
- **补充上下文**：告诉 AI 项目的技术栈约束、团队规模、上线时间等背景信息

> 一句话总结：**AI 画框，人填细节。**

## 开发架构与开发计划

需求拆解清楚后，下一步是设计架构和排计划。这个环节 AI 能帮不少忙，但也最容易踩坑。

### AI 能做什么

- **推荐技术方案**：根据需求场景推荐合适的架构模式（MVC、事件驱动、微服务等），并说明各方案的优劣
- **生成项目结构**：输出目录结构、模块划分、依赖关系图
- **评估工作量**：根据功能点拆分估算开发时间，帮你识别风险点
- **生成接口文档**：根据模块划分快速输出 API 接口定义（路径、参数、返回值）

### 人的工作：核心决策

架构设计是 AI 参与度最低的环节——因为**架构决策本质上是权衡**，需要结合团队能力、项目阶段、运维成本、未来扩展性等 AI 无法完全了解的上下文。

**推荐的做法：**

1. 自己先画一个粗粒度的架构图（模块拆分、数据流向、核心依赖）
2. 让 AI 补充细节（接口设计、数据库表结构、技术选型对比）
3. 人工审查后调整，尤其关注 AI 容易忽略的运维成本和团队学习曲线

### 排计划的技巧

把 AI 拆解出的子任务喂给它，让它帮你估算工时并生成一份排期表。但要注意：AI 的估时通常偏乐观，**建议乘以 1.5 倍作为实际排期**。

## 测试用例

大部分开发者不喜欢写测试用例——枯燥、容易遗漏、还占开发时间。但这恰好是 AI 最擅长的事情之一。

### 让 AI 生成测试用例

把功能描述和代码交给 AI，它能快速生成覆盖正向、异常、边界条件的测试用例。以登录功能为例：

| 用例编号 | 场景 | 预期结果 |
|---------|------|---------|
| TC-001 | 输入正确用户名密码 | 登录成功，返回 Token |
| TC-002 | 密码为空 | 提示"密码不能为空" |
| TC-003 | 连续 5 次密码错误 | 账号临时锁定 30 分钟 |
| TC-004 | 用户名含特殊字符 | 提示"用户名格式错误" |
| TC-005 | Token 过期后访问 | 返回 401，引导重新登录 |

### 关键技巧

- **描述越具体，用例越精准**：不要说"测试登录功能"，要说"用户名 3-20 位字母数字组合，密码至少 8 位含大小写，支持连续登录 5 次失败后锁定 30 分钟"
- **追问边界场景**：多问一句"还有没有遗漏的边界场景？"，AI 通常能补充 3-5 个你没想到的用例
- **审查可行性**：AI 有时会生成过于理论化的场景（比如"用户名超过 10 万字符"），需要人工判断是否值得覆盖

## 代码实现

这是 AI 辅助开发最直观的环节，也是大多数开发者最熟悉的场景。但"会用"和"用得好"之间，差距往往在工作方法上。

### 核心原则：分步写，不要一步到位

```
❌ 错误做法："帮我写一个完整的博客系统"
✅ 正确做法："帮我写一个用户注册接口，使用 Spring Boot，参数校验用 @Valid，密码用 BCrypt 加密"
```

AI 处理小范围、明确的任务时输出质量最高。任务越大，上下文越长，输出越容易跑偏。

### 推荐的分步策略

1. **先写接口签名**：让 AI 生成 Controller/Service 的方法签名和注释，确认入参出参符合预期
2. **再写核心逻辑**：逐方法实现业务逻辑，每段让 AI 生成后人工审查
3. **最后补充细节**：异常处理、日志打印、参数校验、边界条件

这种"骨架 → 血肉 → 皮肤"的方式，比一次性让 AI 输出完整代码更可控。

### 代码审查不要省

AI 生成的代码看起来"能跑"，但可能存在以下问题：

- **风格不一致**：不符合项目现有的编码规范（命名、注释风格、异常处理方式）
- **遗漏边界处理**：只覆盖了 Happy Path，对空值、并发、超时等场景考虑不足
- **过度设计**：引入不必要的设计模式或第三方依赖，增加维护成本
- **安全隐患**：SQL 拼接、敏感信息硬编码等低级但常见的问题

**建议：** 每段 AI 生成的代码，花 30 秒扫一眼，确认逻辑符合预期、风格与项目一致再提交。

## 自动化测试验证

代码写完了，自动化测试是保障质量的最后一道防线。AI 在这个环节的价值在于：快速生成测试代码 + 持续执行验证。

### AI 帮你写测试

AI 能根据实现代码自动生成单元测试和集成测试，覆盖你容易忽略的边界场景：

```java
// AI 生成的单元测试示例
@Test
void testLoginSuccess() {
    LoginRequest request = new LoginRequest("admin", "P@ssw0rd");
    LoginResponse response = authService.login(request);
    assertNotNull(response.getToken());
    assertEquals("admin", response.getUsername());
}

@Test
void testLoginWithEmptyPassword() {
    LoginRequest request = new LoginRequest("admin", "");
    assertThrows(ValidationException.class, () -> {
        authService.login(request);
    });
}

@Test
void testLoginWithLockedAccount() {
    // 模拟连续 5 次失败后账号被锁定
    for (int i = 0; i < 5; i++) {
        try { authService.login(new LoginRequest("admin", "wrong")); }
        catch (Exception ignored) {}
    }
    assertThrows(AccountLockedException.class, () -> {
        authService.login(new LoginRequest("admin", "P@ssw0rd"));
    });
}
```

![AI 辅助测试验证流程](/assets/images/test-automation.svg)

### 持续验证的三个阶段

自动化测试的价值不在于"写了一次"，而在于**持续执行**：

- **本地开发阶段**：每次改代码跑一次单元测试，确保不破坏已有功能
- **CI/CD 阶段**：提交代码后自动运行全量测试，失败则阻断发布流程
- **回归测试阶段**：每次迭代全量跑一遍，发现隐藏的功能退化

## 总结

| 阶段 | AI 做的事情 | 人做的事情 |
|------|------------|-----------|
| 需求拆分 | 将模糊需求结构化，补充遗漏维度 | 删减、排序、补充业务上下文 |
| 架构设计 | 推荐方案、生成目录结构和接口文档 | 核心决策、权衡取舍、评估运维成本 |
| 代码实现 | 按分步指令生成代码片段 | 审查逻辑、统一风格、排查安全隐患 |
| 测试用例 | 生成覆盖全场景的测试用例 | 审查边界条件可行性，补充业务特有场景 |
| 自动化验证 | 编写测试脚本、执行测试 | 维护测试套件、分析失败原因 |

**核心观点：** AI 是副驾驶，不是自动驾驶。它擅长**广度**——快速生成大量选项和内容，覆盖你可能遗漏的维度；而人擅长**深度**——理解业务上下文、做出权衡决策、把控最终质量。

两者结合，才是高效的开发方式。
