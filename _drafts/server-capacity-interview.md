## 先说结论

**没有标准答案，但面试官想听的是你的分析过程。**

一句话回答：一台服务器一个 IP，理论上能支撑 **数万到数百万** 并发连接，实际上取决于五层瓶颈——端口号、文件描述符、内存、CPU、带宽。只要有一层不够，就是天花板。

## 第一层：端口号只有 65535 个？

面试官最爱挖的第一个坑。

> "TCP 端口号是 16 位，范围 0~65535，所以最多 65535 个连接，对吧？"

**错。** 四元组决定一条 TCP 连接：

```
{源 IP, 源端口, 目的 IP, 目的端口}
```

服务器固定了目的 IP 和目的端口（比如 443），变化的只有客户端 IP 和客户端端口。所以：

| 客户端 IP 数 | 每个客户端可用端口数 | 服务器侧最大连接数 |
|-------------|-------------------|------------------|
| 1 个 IP | ~64512（去掉特权端口） | ~64512 |
| 1 个 C 段（256 个 IP） | ~64512 | ~1650 万 |
| 全 IPv4（理论） | ~64512 | ~2⁴⁸ |

**关键结论**：作为服务端，端口不是瓶颈。65535 是客户端出口端口的限制，不是服务端入口的限制。服务端只监听一个端口（如 443），就能接受海量连接。

## 第二层：文件描述符上限

Linux 中一切皆文件，每个 TCP 连接占用一个文件描述符（fd）。

### 默认值

```bash
# 查看系统级 fd 上限
cat /proc/sys/fs/file-max
# 通常为 95535 或更高

# 查看单个进程 fd 上限
ulimit -n
# 通常为 1024
```

单进程默认只有 1024 个 fd，去掉标准输入输出和内部使用的约 10 个，**实际能承载约 1000 个并发连接**。这才是很多人说"一台服务器只能扛 1000 并发"的真正来源。

### 调优后

```bash
# 临时提升单进程 fd 上限
ulimit -n 1000000

# 永久修改：/etc/security/limits.conf
* soft nofile 1000000
* hard nofile 1000000

# 系统级上限
echo 2000000 > /proc/sys/fs/file-max
```

调优后单进程可支撑百万级 fd。Nginx、Netty 等高性能服务器在生产环境通常配置为 50 万~100 万。

## 第三层：内存

每个 TCP 连接都要占用内存，包括：

| 组成部分 | 内核态 | 用户态 | 合计 |
|---------|--------|--------|------|
| Socket 缓冲区 | 接收 4KB~6MB（动态） | — | ~10KB 起 |
| 协议控制块（TCB） | ~2KB | — | ~2KB |
| 应用层对象 | — | 视框架而定 | ~2KB~10KB |

### 最小估算

假设每个连接的接收/发送缓冲区调到最小（各 4KB）：

| 每连接内存 | 服务器内存 | 可支撑连接数 |
|-----------|-----------|------------|
| ~10KB | 16GB | ~160 万 |
| ~10KB | 64GB | ~640 万 |
| ~10KB | 256GB | ~2560 万 |

### 实际估算

生产环境不会把缓冲区调到最小，加上应用层对象（HTTP 上下文、Session、业务对象），每连接通常占 **20KB~100KB**：

| 每连接内存 | 服务器内存 | 可支撑连接数 |
|-----------|-----------|------------|
| ~50KB | 16GB | ~30 万 |
| ~50KB | 64GB | ~130 万 |
| ~100KB | 16GB | ~16 万 |

**关键结论**：内存是第一个真正的物理瓶颈。16GB 内存、每连接 50KB，大约 30 万并发。

## 第四层：CPU

CPU 不是"连接数"的瓶颈，而是"请求处理速度"的瓶颈。

### 两个不同的概念

- **并发连接数**：同时建立的 TCP 连接数量（可以空闲挂着）
- **QPS（每秒请求数）**：每秒能处理多少个请求

10 万个空闲连接（比如 WebSocket 长连接、IM 推送），CPU 几乎不干活。但如果 10 万个连接同时发请求，CPU 就是瓶颈。

### QPS 估算

| 请求处理耗时 | 单核 QPS | 32 核 QPS | 128 核 QPS |
|------------|---------|----------|-----------|
| 1ms | 1000 | 32000 | 128000 |
| 5ms | 200 | 6400 | 25600 |
| 20ms | 50 | 1600 | 6400 |

> 32 核服务器，每个请求 5ms，理论 QPS ≈ 6400。考虑上下文切换、GC、锁竞争，实际打 6~7 折，约 4000~4500 QPS。

**关键结论**：CPU 决定了 QPS 而不是连接数。面试时一定要区分"并发连接数"和"并发请求数"，这是加分项。

## 第五层：网络带宽

最后一个常被忽略的瓶颈。

### 估算公式

```
每秒处理字节数 = 带宽 / 8
最大 QPS = 每秒处理字节数 / 每请求平均字节数
```

### 具体计算

| 服务器带宽 | 实际吞吐 | 每请求 1KB | 每请求 10KB | 每请求 100KB |
|-----------|---------|-----------|------------|-------------|
| 1Gbps | ~100MB/s | 10 万 QPS | 1 万 QPS | 1000 QPS |
| 10Gbps | ~1GB/s | 100 万 QPS | 10 万 QPS | 1 万 QPS |
| 25Gbps | ~2.5GB/s | 250 万 QPS | 25 万 QPS | 2.5 万 QPS |

> 假设接口返回 10KB 数据，1Gbps 网卡的理论上限约 1 万 QPS。如果应用层还能扛更多 QPS，带宽就成了天花板。

## 满分回答模板

> 一台服务器一个 IP，并发连接数受五层瓶颈约束：
>
> 1. **端口号不是瓶颈**——四元组模型下，服务端单端口可接受海量连接
> 2. **文件描述符**——默认 1024，调优后可达百万级
> 3. **内存**——16GB、每连接 50KB，约 30 万并发连接
> 4. **CPU**——不决定连接数，决定 QPS。32 核、5ms/请求，约 4000~6000 QPS
> 5. **带宽**——1Gbps、10KB/请求，约 1 万 QPS
>
> 实际生产中，先调 fd 和内核参数，再根据内存估算连接数上限，最后用 CPU 和带宽约束 QPS。**木桶效应，最短那块板决定天花板。**

## 真实生产参考

| 场景 | 典型配置 | 并发连接数 | QPS |
|------|---------|-----------|-----|
| Nginx 反向代理 | 32C 64G 10Gbps | 50 万~100 万 | 5 万~10 万 |
| Netty IM 推送 | 16C 32G 1Gbps | 50 万~100 万 | 1 万~5 万 |
| Spring Boot API | 8C 16G 1Gbps | 1 万~5 万 | 2000~5000 |
| Go HTTP 服务 | 4C 8G 1Gbps | 10 万~20 万 | 1 万~3 万 |

## 调优清单

面试如果被追问"怎么提升"，按顺序回答：

```bash
# 1. 提升文件描述符
echo 2000000 > /proc/sys/fs/file-max
ulimit -n 1000000

# 2. 调整 TCP 参数
echo "net.ipv4.tcp_max_syn_backlog = 65535" >> /etc/sysctl.conf
echo "net.core.somaxconn = 65535" >> /etc/sysctl.conf
echo "net.ipv4.tcp_tw_reuse = 1" >> /etc/sysctl.conf
echo "net.ipv4.tcp_fin_timeout = 15" >> /etc/sysctl.conf

# 3. 减小 TCP 缓冲区（用内存换连接数）
echo "net.ipv4.tcp_rmem = 4096 87380 16777216" >> /etc/sysctl.conf
echo "net.ipv4.tcp_wmem = 4096 65536 16777216" >> /etc/sysctl.conf

# 4. 应用层优化
# - 用 NIO / Epoll 替代 BIO
# - 连接复用（HTTP Keep-Alive、连接池）
# - 异步化（CompletableFuture / 协程）
# - 减小每请求内存占用
sysctl -p
```

## 一句话总结

**65535 不是答案，是陷阱。真正的天花板是木桶效应——fd、内存、CPU、带宽，哪块最短就是哪块。** 面试官要的不是数字，是你层层拆解的思路。
